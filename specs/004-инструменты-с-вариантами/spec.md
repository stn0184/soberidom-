## Проблема

Новичок не знает, чем пилить доску и чем забивать гвозди, а сайт сейчас
отвечает сухо: «Циркулярная пила — купить», одной строкой «альтернатива:
ножовка». Выбора нет, объяснения «дешевле, но дольше» нет, и человек либо
скупает магазин, либо идёт спрашивать продавца. ВИДЕНИЕ §2.4: у каждой
потребности — 2–3 варианта инструмента с объяснением «зачем, дешевле или
дороже, дольше или быстрее, можно ли обойтись, купить или арендовать», и
**право выбора у человека**.

Вторая половина проблемы — контент некуда положить: у `project_tools` нет
ни формы, ни API в админке, список эталонного проекта пуст, и экран
`/tools` и блок «И это понадобится» (этап 003) показывают «список пуст».

## Решение

**Данные** — миграция `026_tool_variants.sql` (SQL в `SPEC.md` §2.4 и
§2.6 тем же коммитом):

- `project_tools` остаётся **потребностью** («Пилить доски», «Забивать
  гвозди»): `name`, `category`, `reason` (зачем это вообще нужно на
  стройке), `days_needed`, `stage_codes`, `sort`. Колонки `recommendation`,
  `approx_price_minor`, `approx_rent_day_minor`, `alternative` не удаляются
  (существующее не ломаем), но новый код их не читает и не пишет.
- Новая таблица `tool_variants`: `id`, `tool_id → project_tools on delete
  cascade`, `name` («Ножовка», «Циркулярная пила»), `description` (чем
  хорош и чем плох, для бабушки), `recommendation` `buy | rent |
  borrow_or_buy_cheap`, `price_minor` (ориентир покупки), `rent_day_minor`
  null (ориентир аренды в сутки), `speed_note` («в 5 раз медленнее»,
  «быстро»), `is_beginner_choice` bool (ровно один на потребность —
  проверяется приложением, не БД), `sort`. RLS: `read_all` + `admin`, как
  у `project_tools`.
- Новая таблица `user_tool_choices`: `purchase_id → purchases`, `tool_id →
  project_tools`, `variant_id → tool_variants`, `unique (purchase_id,
  tool_id)`, `updated_at`. RLS «своё» по `purchases.user_id = auth.uid()` —
  точно как `uprices_own` в §2.6.

**API:**

- `GET /api/my/[purchaseId]/tools` → `{ data: { summary, tools }, meta:
  { currency } }`, где `tools[]` = `{ id, name, category, reason,
  daysNeeded, stages, variants: [{ id, name, description, recommendation,
  priceMinor, rentDayMinor, speedNote, isBeginnerChoice }],
  chosenVariantId }`. `chosenVariantId` — из `user_tool_choices`, иначе
  `null`. `summary.buyTotalMinor` / `rentTotalMinor` считаются по
  **действующему варианту** каждой потребности: выбранный, иначе
  `is_beginner_choice`, иначе первый по `sort` (аренда = `rent_day_minor ×
  days_needed`, как сейчас). Потребность без вариантов в ответ не попадает.
- `PUT /api/my/[purchaseId]/tools/choice` `{ toolId, variantId }` —
  upsert в `user_tool_choices`; вариант обязан принадлежать этой
  потребности и потребность — проекту покупки, иначе `VALIDATION_ERROR`.
  Гард `requireOwnerPurchase`, формат ошибок SPEC 3.0.
- `GET /api/my/[purchaseId]/supplies` — `tools[]` теперь отдаёт потребность
  с **действующим вариантом** (`variant: { name, recommendation,
  priceMinor, rentDayMinor }`, `isChosen: boolean`); контракт
  `SuppliesTool` в `build-types.ts` меняется.
- Админка (`requireAdmin`, Zod из `src/lib/zod/admin.ts`):
  `GET/POST /api/admin/tools?projectId=`, `PATCH/DELETE
  /api/admin/tools/[id]`, `POST /api/admin/tool-variants`, `PATCH/DELETE
  /api/admin/tool-variants/[id]`. Схемы `toolSchema`, `toolVariantSchema`
  зеркалят таблицы, `*UpdateSchema = partial()` — как у `partSchema`.

**Экран `/my/[purchaseId]/tools`** (переделка `tools-view.tsx`):

- Верх без изменений: две Stat-Card «Купить ≈ …» / «Арендовать ≈ …», но
  суммы — по действующим вариантам, с подписью «по вашему выбору».
- Карточка потребности: заголовок («Пилить доски»), `reason`, чипы
  этапов, ниже **варианты** — `tool-variant-card.tsx` (≤200 строк):
  радио-карточки в ряд (`sm:grid-cols-2 lg:grid-cols-3`), у каждой
  название, бейдж купить / аренда / одолжить, цена (покупка; аренда × дни,
  если есть), `speed_note` серым, `description`, бейдж «Для новичка» у
  `is_beginner_choice`. Клик — `PUT /choice`, optimistic, toast при ошибке
  и откат; выбранная подсвечена (`ring-2 ring-primary`), у неё подпись
  «Ваш выбор». Пока выбора нет — подсвечен «для новичка» с подписью
  «Советуем новичку», без записи в базу.
- Фильтр по категории остаётся. Пустое состояние — как сейчас.

**Блок «И это понадобится»** на экране этапа (003): у потребности одна
строка — действующий вариант, бейдж, цена; подпись «ваш выбор» или
«советуем новичку»; ссылка «Выбрать другой →» на `/tools`.

**Админка** — новая вкладка «Инструменты» в `steps-manager.tsx` рядом с
«Этапы», «Детали», «Опции» (`ru.admin.steps.tabTools`): `tools-panel.tsx`
— таблица потребностей проекта (название, категория, этапы, число
вариантов, бейдж «нет варианта для новичка» красным), кнопка «Добавить»,
меню строки «Изменить / Удалить» (`ConfirmDelete`) — по образцу
`parts-panel.tsx`; `tool-form.tsx` в `Sheet` — поля потребности +
`tool-variants-field.tsx`: список вариантов с инлайн-редактированием и
переключателем «для новичка» (ровно один). Каждый файл ≤200 строк.

**Контент** — сид `027_seed_tools_homesteaders.sql` для проекта
`de300000-0000-4000-8000-000000000100` (Homesteader's Cabin), идемпотентно
(`on conflict do nothing` по фиксированным UUID). Состав — ровно этот, без
самодеятельности; цены — ориентиры 2026 в RUB, правятся в админке:

## Чего не делаем

- Не заводим стоимость инструментов в смету и фин-отчёт: Stat-Card на
  `/tools` — ориентир, не позиции сметы. Отдельный этап, если понадобится.
- Не делаем видеоуроки к инструментам (ВИДЕНИЕ §2.5 — после продаж).
- Не добавляем фильтр «только для этапа N» на `/tools` (SPEC 4.12a его
  упоминает, но это отдельная S-правка); фильтр по категории остаётся.
- Не удаляем старые колонки `project_tools` и не переносим их значения:
  строк в проде нет (демо-сид 005 — единственный источник, и он к
  эталонному проекту не относится).
- Не показываем инструменты на витрине проекта (комментарий SPEC §2.4
  «список показываем и на витрине» — не реализован и не в этом этапе).
- Не считаем «сколько сэкономили выбором» — только суммы по выбору.
- Не заводим выбор варианта на экране этапа (003): там показ и ссылка
  «Выбрать другой →»; выбор — только на `/tools`.

## Приёмка

- КОГДА покупатель открывает `/my/[id]/tools` на проекте с
  инструментами, каждая потребность ДОЛЖНА показать все свои варианты
  с названием, бейджем купить/аренда/одолжить, ценой, пометкой
  «дольше/быстрее» и объяснением; вариант «для новичка» помечен бейджем.
- КОГДА выбора ещё нет, вариант «для новичка» ДОЛЖЕН быть подсвечен с
  подписью «Советуем новичку», а в `user_tool_choices` записи нет.
- КОГДА покупатель кликает другой вариант, он ДОЛЖЕН подсветиться с
  подписью «Ваш выбор» без перезагрузки, а после обновления страницы
  выбор ДОЛЖЕН сохраниться.
- КОГДА выбор изменён, суммы «Купить ≈ …» и «Арендовать ≈ …» ДОЛЖНЫ
  пересчитаться по действующим вариантам всех потребностей.
- КОГДА покупатель открывает экран начала этапа, блок «И это
  понадобится» ДОЛЖЕН показать по одной строке на потребность этапа —
  действующий вариант с подписью «ваш выбор» или «советуем новичку» и
  ссылкой «Выбрать другой →» на `/tools`.
- КОГДА `PUT /choice` получает вариант чужой потребности или потребность
  чужого проекта, API ДОЛЖЕН ответить `VALIDATION_ERROR` в формате
  `{ error: { code, message } }`; чужая покупка — 404.
- КОГДА у потребности нет ни одного варианта, она НЕ ДОЛЖНА попасть в
  ответ `/tools` и `/supplies`.
- КОГДА админ открывает «Этапы и шаги» → вкладка «Инструменты» для
  проекта, он ДОЛЖЕН видеть таблицу потребностей с числом вариантов и
  красный бейдж у потребности без варианта «для новичка».
- КОГДА админ сохраняет потребность с вариантами, где «для новичка»
  отмечено дважды или ни разу, форма ДОЛЖНА не дать сохранить и объяснить
  почему.
- КОГДА админ удаляет потребность, её варианты и выборы покупателей
  ДОЛЖНЫ удалиться каскадом (после подтверждения `ConfirmDelete`).
- КОГДА миграция 027 применена, у Homesteader's Cabin ДОЛЖНО быть ровно
  15 потребностей из таблицы выше, у каждой — ровно один вариант «для
  новичка»; повторное применение ничего не дублирует.
- Ни одной русской строки в JSX новых компонентов: все — из `ru.ts`.
